# 技术设计自评与迭代记录

日期：2026-10-10 · 评审方式：文档作者自行交叉检查用户故事、技术初稿和异常路径；不是独立专家评审，也不是代码测试。

## 1 结论

维持“本地数据库＋文字解析后端”的首版方案。数据库、服务和传输边界已能支撑任务拆分；不需要为了形式完整加入服务器库存数据库。照片原子保存、历史状态、重复提交、迟到响应是主要实现检查点。

完成顺序：写三份 v0.1 技术初稿 → 对照故事与失败场景自评 → 修改为 v0.2 → 复核字段与引用。当前交付为修订后的版本，下面保留实际修改原因，不保留两套互相冲突的规范。

## 3 修订后按场景复核

| 场景 | 设计推演结果 | 实施时必须验证 |
| --- | --- | --- |
| 图片写入失败 | 图片与观察、包装、回执同事务，整体回滚 | 注入失败后重新查库，无半条记录 |
| 已提交但界面失败后重试 | 先查命令回执，再查 revision，返回原结果 | 重复 ID 不产生第二条观察 |
| 两个标签页同时反馈 | 一个先递增 revision，另一个返回冲突 | 真实浏览器双页面测试 |
| 背包未找到后更新行李箱 | 当前观察按 seq 选，旧反馈不再参与 | 当前状态、历史和照片绑定均正确 |
| 再次在原处找到 | 新 found 反馈更新确认时间，原照片时间不改变 | UI 不将旧照片显示为刚拍摄 |
| 相册照片没有可信时间 | capturedAt=null，添加/确认时间分开 | 页面显示拍摄时间未知 |
| AI 回应时用户已经转手工 | generation 与草稿版本检查拒绝旧响应 | 网络延迟用例不覆盖人工编辑 |
| 后端不可用 | 手工流程不依赖 HTTP | 已加载页面仍能保存与查询 |
| 新用户或站点换端口 | origin 下独立数据，不进行静默种子注入 | 空态与运行说明正确 |

这些是设计推演结果，不表示测试已通过。

## 4 留给实现阶段的明确事项

1. 安装并锁定兼容依赖，验证 Node 24 与最终 Vite/Fastify 插件组合。
2. 选择真实文字模型与 SDK；明确配置、费用预算和超时是否可接受。未配置前可使用明确标识的 Mock 完成接口开发。
3. 将 JSON Schema 写成实际文件，生成 OpenAPI 并跑契约检查；当前文档中的示例不是可执行 schema。
4. 验证 iOS/Android 文件选择与 JPEG 转码；24 MP/10 MiB 输入预算与内存峰值需真机测试，超预算或无法解码则明确拒绝。
5. 图片入口、包装选择与异常界面尚未补入静态原型；实施时按用户故事补齐。
6. 本地存储无云备份、无离线启动承诺；若需求变更，先更新架构与故事。

本轮仅修改设计文档，没有运行应用构建、数据库事务或模型测试，不将文档自评称作工程验收。
