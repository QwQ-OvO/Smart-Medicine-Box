# 家庭常备药位置线索｜MVP 决策草案

日期：2026-10-10<br/>
状态：待验证，尚未进入最终开发定稿<br/>
适用场景：C「年轻人 × 家庭常备药」

## 1. 当前决策

**第一版聚焦：用户已经知道要找哪种药，但不知道应该从哪里开始找。**

优先验证的方案是：提供带时间和来源的位置线索，帮助用户确定查找起点，减少盲目翻找。

暂不承诺准确掌握实时库存、避免重复购买或减少过期浪费。这些效果尚未得到验证。

## 2. 决策依据

| 证据 | 支持的判断 | 局限 |
|---|---|---|
| P01 I09、I10：会查找行李箱、桌面、背包口袋和杂物袋 | 查找涉及多个位置 | 没有现场观察或计时 |
| P01 I08、I10：不清楚未找到的药是否用完 | 记忆不足以确认当前状态 | 没有实物核对 |
| P01 I11：预计无法持续更新记录 | 高频维护可能妨碍使用 | 自报意愿，不是长期行为 |
| 后续澄清：“主要是不知道从哪里找” | 优先研究位置线索 | 仍属于用户自述 |
| 公开资料 R1、R2 | 库存认知可能与实际情况不同 | 不能直接证明本方案有效 |
| 公开资料 R4、R5 | 应将录入与习惯适配计入成本 | 研究对象与本项目不同 |
| 方案研究 S1—S4 | 自动采集也有范围与条件限制 | 不证明家庭长期使用效果 |

文献编号对应已有公开研究汇总；本草案不增加未经核验的研究结论。

## 3. 目标用户与核心任务

**目标用户**

药品分散放在住处与随身物品中，不愿逐次登记存取，需要寻找一种已明确药品的人。

**核心任务**

> 查看已有的位置线索，决定先去哪里找，并根据实际查找结果确认或纠正线索。

**核心价值假设**

即使位置记录无法保持实时准确，历史线索也可能比完全凭记忆翻找更有帮助，而且收益能够超过记录与纠错成本。

这是本轮需要验证的假设，不是已经证明的结论。

## 4. 候选方案与取舍

| 方案 | 机制 | 当前决定 |
|---|---|---|
| 固定收纳 | 设置主要收纳位置，允许正常随身携带 | 作为比较基准 |
| 低频位置记录 | 整理或放置时记录，需要时查询 | 优先验证 |
| 药箱自动感知 | 记录包装在感知范围内的状态 | 暂缓，先确认覆盖范围是否有价值 |
| 纯对话查找助手 | 帮助梳理可能位置 | 暂缓，缺乏额外信息时可能增加负担 |

优先验证低频位置记录，是因为它能够直接回应“不知道从哪里找”，且不必先接入硬件。但用户是否愿意记录、信息是否经常失效，仍是主要风险。

**药箱的候选角色**是家庭主要收纳点或位置记录入口，尚未定稿。若最终流程完全不依赖药箱，需要重新说明与题目主题的联系。

## 5. 最小任务闭环

1. **留下线索**：用户在自然整理或放置时提供药品名称与位置。
2. **核对保存**：确认内容，保存记录时间和来源。
3. **发起查找**：输入已经明确的药品名称。
4. **查看线索**：展示最近记录的位置，说明当前是否仍在尚未确认。
5. **实际寻找**：用户前往相应位置。
6. **反馈结果**：选择“找到了”或“这里没找到”，必要时更新线索。

示例展示：

> **布洛芬**<br/>
> 最近记录位置：背包前袋<br/>
> 记录时间：10 月 8 日<br/>
> 来源：你当时确认的位置<br/>
> 当前是否仍在：未确认

没有记录时，明确显示“暂无位置线索”，不生成看似真实的位置。

## 6. 关键异常

**异常：按记录位置查找，仍然没有找到药。**

处理原则：

- “这里没找到”不等于库存为零，也不等于已经用完。
- 保留原始位置记录，新增本次查找结果。
- 标记该位置“本次未找到”，避免继续显示成当前确认位置。
- 用户后来找到药后，可以确认新的位置。
- 没有其他记录时，明确说明没有更多线索。

同名多盒药不能默认视为同一个实物。最小原型可以先限制为一个可区分包装，但应说明这一限制。

## 7. 智能能力的候选角色

候选能力：

> 将用户提供的自然语言位置描述整理为结构化记录，经用户核对后保存。

例如，将“这盒布洛芬放进黑色背包前袋了”整理成药名、容器和具体位置。

需要验证它是否比手工输入更省力，比较时计入核对和纠错时间。

边界：

- AI 不推断未观察到的移动、消耗或隐藏库存。
- 有歧义时请求确认，不能补造事实。
- 识别失败时允许手动填写。
- 不涉及诊断、选药或治疗方案调整。
- 使用 Mock 时明确标注，不能据此宣称智能能力有效。

## 8. 第一版开发边界

| 类别 | 范围 |
|---|---|
| 必须跑通 | 输入、核对、保存、查询、位置展示、查找反馈 |
| 必须处理 | 历史位置未找到的异常 |
| 基础状态 | 无记录、处理中、失败、历史线索、本次未找到 |
| 可采用 | 本地存储、明确标注的外部能力 Mock |
| 暂缓 | 账户体系、多人协作、实时数量、自动补货、有效期提醒、复杂硬件 |

逻辑职责划分：

```text
界面：输入、位置线索、确认和异常展示
  ↓
任务流程：记录、查找、反馈、纠错
  ↓
业务规则：校验、历史记录与当前观察的区分
  ↓
能力适配：存储、智能解析、可选设备事件
```

技术栈和组件库应在检查现有项目后决定。真实模型调用如涉及密钥，应由服务端处理。

## 9. 验证计划

| 假设 | 验证方式 | 需要改变方向的信号 |
|---|---|---|
| 不知道从哪里找造成实际负担 | 观察一次自然找药 | 很快找到，现有方式已经足够 |
| 用户接受低频记录 | 实际完成一次记录 | 找不到愿意操作的自然时机 |
| 历史位置仍有帮助 | 后续自然查找或情境试走 | 记录频繁误导，纠错成本过高 |
| 用户理解信息局限 | 解释页面并处理未找到异常 | 将历史位置理解为当前保证 |
| AI 降低输入成本 | 与手工输入比较 | 核对和纠错抵消节省的操作 |

观察应在非紧急情况下进行，不提前整理或提示位置。记录查找顺序、耗时、结果及后续行动。

同一物品的重复查找会产生记忆效应，不能据此宣称方案提高效率。情境试走用于发现交互问题，不能证明长期采用。

## 10. 下一步与开发准入条件

**下一步按顺序执行：**

1. 观察一次真实找药，确认困难主要发生在选择查找位置。
2. 试走“整理或放置时记录，下次查找时查看”。
3. 演示记录位置未找到的异常，观察理解与纠错。
4. 根据结果选择继续、缩小承诺或返回问题探索。
5. 再确定页面、数据结构及现有项目的最小改动。

**进入开发前，应能回答：**

- 位置信息从哪里来？
- 用户什么时候愿意记录？
- 相比原来的方式，具体帮助是什么？
- 信息错误后如何恢复？
- 哪些判断仍然没有验证？

若时间不足，可以带着明确的假设进入原型开发，但必须把长期准确性、维护意愿和使用效果保留为待验证项。
