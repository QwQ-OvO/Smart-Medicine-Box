# 家庭药品位置线索竞品与替代方案分析

资料核验日期：2026-10-11。适用对象：25–35 岁、无长期固定用药管理需求、常备药分散存放的年轻人。

当前产品解决的是“已经知道要找哪盒药，决定先去哪里找”。最值得优先比较的是已有的位置与收纳工具；服药提醒和自动分药产品用于辨别任务边界。

**主要判断：药品建档、位置管理、照片和 AI 录入已有同类能力。本项目值得验证的价值是：在用户不愿逐次更新的条件下，用带时间和来源的历史线索帮助查找，并在未找到后完成纠错。这个组合尚未证明优于现有工具，也不能据本轮检索宣称市场空白。**

## 1 分析依据与证据范围

本分析承接[初步产品设计](../初步产品设计.md)、[MVP 决策草案](../MVP%20决策草案.md)和[项目 README](../../README.md)。产品设计保留的是早期方案状态；当前实现范围以 README 为准。既有[公开研究综述](家庭药品管理_公开研究与方案证据综述.md)第 5 节有 Medisafe、Hero 案例，但未形成围绕找药任务的系统竞品比较，本篇补足这一部分。

本轮核对了开发者发布的应用商店说明、官方帮助中心、官网及开源仓库。它们支持“公开提供或宣称何种功能”，不能证明实际效果、识别准确率、维护成本或用户留存。未安装或实操竞品；“未确认”表示所查资料不足，不表示产品没有该能力。本文的适配性、维护风险和优先级属于基于功能机制的分析。

选取 7 个产品与 2 类非专用替代方案：覆盖中文家庭药品管理、位置收纳、库存维护、服药协作和硬件分药。并非市场份额排名；未核实 Android、中国大陆以外商店或所有付费层的可用性。商店“免费”只代表页面的下载标示，不能据此认定全部功能免费。

## 2 产品与任务关系

| 对象 | 核验到的功能事实 | 与本项目的关系及比较重点 |
| --- | --- | --- |
| **i药管家** | 中国区 iPhone 商店说明包含条码添加、不同药箱与共享药箱、有效期及库存阈值提醒。[S1] | 同领域竞品。比较“按药箱分类找药”是否已足够，不应把药品清单本身当成创新 |
| **收起来** | 开发者说明支持 AI 对话录入、名称及位置等字段、按位置查看、搜索和家庭共享；页面含 App 内购买。[S2] | 核心任务的直接替代，优先级最高。与一句话记位置明显重叠，应比较完整查找与纠错成本 |
| **收纳先生** | 开发者说明包含物品查找、空间视图、位置、智能识别及多人协作。[S3] | 核心任务的直接替代。需比较用户理解具体容器或位置的速度 |
| **HomeBox** | 官方仓库列出位置、标签、自定义字段、搜索、物品图片和浏览器界面，并提供自托管启动方式。[S4] | 开源机制参照。能检验通用物品档案是否足够；部署与备份成本也应计入 |
| **Grocy** | 官网提供家庭库存、条码、最低库存及到期管理；官方旧教程包含采购、消耗、位置转移与盘点。[S5][S6] | 库存维护参照。适合比较持续记账与低频位置记录的成本差别 |
| **Medisafe** | 官方页面围绕服药计划、提醒与记录；帮助中心区分 Medfriend 查看协作与代管档案。[S7][S8] | 相邻任务产品。主要解决用药执行及照护协作，不能用它的提醒能力推导找药效果 |
| **Hero** | 官方说明设备可管理最多 10 种药、最多 90 天供给；应用另可登记 10 种设备外药品。[S9] | 硬件参照。集中分药与分散包装找回不同；登记设备外药品不等于自动定位 |

本项目目前只支持单设备本地记录，真实 AI 适配尚未实测；照片与历史反馈已记录为 Demo 能力。竞品的共享、扫码等能力可能更适合其他用户，不应以本项目的窄范围推导全面优越性。

## 3 围绕一次找药的能力比较

表中“已说明”仅指公开资料明确列出；“待实测”是实际体验或细节尚未核实。

| 方案 | 确定查找起点 | 录入与维护方式 | 历史线索和未找到处理 |
| --- | --- | --- | --- |
| i药管家 [S1] | 药箱分类；口袋级位置未确认 | 扫码建档；实物移动如何更新待实测 | 未确认专门的查找失败流程 |
| 收起来 [S2] | 位置筛选与搜索已说明 | AI 对话等录入；日常移动操作待实测 | 版本记录提及库存日志，但不能据此确认位置观察及失败反馈机制 |
| 收纳先生 [S3] | 空间视图、查找与位置已说明 | 识别与导入已说明；移动操作待实测 | 未确认“这里没找到”的专门语义 |
| HomeBox [S4] | 搜索及位置组织已说明 | 建立物品档案；位置变更操作待实测 | 未确认按查找结果标记线索失效 |
| Grocy [S5][S6] | 可记录存放位置 | 采购、消耗、转移、盘点；旧教程不能作为当前界面规范 | 盘点面向账实核对，不能直接等同一次寻找失败 |
| Medisafe [S7][S8] | 所查资料聚焦服药计划 | 配置药品计划并记录执行情况 | 服药或漏服记录不能直接代表是否找到包装 |
| Hero [S9][S10] | 设备集中存放、按计划分药 | 装填、配置和补充；设备外另行登记 | 设备外包装具体位置及失败查找处理未确认 |
| 本项目 | 药名 → 包装 → 最近位置、时间、来源 | 手工或一句话核对；照片可选，不要求逐次登记 | 保留观察和反馈；未找到不等于用完；在别处找到后追加位置 |

不能将竞争对手“未确认”的格子直接计为本项目得分。下一轮应先实操收起来和收纳先生，检查其备注、日志、移动与归档能否完成相同任务，再判断差异是否成立。

## 4 关键竞争判断

### 4.1 一句话录入不足以建立差异

收起来已经公开列出对话录入与位置字段。[S2] 对本项目而言，“接入 AI”只是候选输入方式。竞争评价应覆盖输入、等待、核对、修改和保存的总成本，而非只数输入框或按钮。

优先保留可独立使用的手工路径；若真实 AI 的核对与纠错抵消节省的时间，应把手工作为默认入口。当前 Mock 不能参与真实识别效果比较。

### 4.2 失效线索的处理值得验证

本项目的具体机制是：记录对某盒药的一次位置观察，显示其发生时间，接受“这里没找到”，随后允许结束或追加新观察。它的价值假设是降低错误线索继续误导用户的机会。

这一机制也有成本：用户需要反馈，结果页增加状态信息，而且一次未找到可能只是没看见。测试时必须同时观察操作负担与误解，不能只展示理想纠错流程。竞争对手是否已经通过日志或自定义状态解决相同问题，仍需实操核实。

### 4.3 收纳照片应保留环境信息

HomeBox 已提供物品图片，[S4] 因而“支持照片”本身不构成优势。本项目需要验证的是现场照片是否帮助辨认具体抽屉、背包口袋或容器。

拍摄引导应鼓励保留能辨认位置的环境线索。照片随观察保存，换位置后不自动沿用；旧图不应被理解为实时画面。是否比文字有效，要用实际辨认任务比较。

### 4.4 库存与硬件能力有不同的前提

Grocy 的库存流程依赖采购、消耗、转移或盘点记录；其旧教程还要求建立位置与数量单位。[S6] 由此推论：若用户不愿持续维护，直接复制完整库存模式可能与本项目目标冲突，但具体负担需要实测。

Hero 展示的是集中装填、提示和分药的闭环。[S9][S10] 它不能作为“药箱知道背包里的药放在哪里”的证据。本项目应先证明记录入口的价值，再决定硬件是否能够覆盖足够多的真实动作。

## 5 非专用替代方案

以下是比较基准的构造，不是对某一品牌应用的功能断言。实际测试使用参与者已有的工具。

| 替代方案 | 为什么可能更合适 | 需要比较的局限 |
| --- | --- | --- |
| 固定收纳位置与容器标签 | 不需要额外数字录入；用户可能凭稳定习惯快速找到 | 搬动、随身携带或跨容器放置时，固定收纳能否覆盖实际需要 |
| 已有备忘录中的文字或照片 | 可直接记录“药名＋包装标签＋位置＋日期”；不必采用新应用 | 是否容易检索到正确包装、区分旧记录，以及在失效后更新；历史与检索能力取决于所选工具 |

如果固定收纳已解决绝大多数查找，项目不应再要求使用应用。如果备忘录在总成本、可理解性和找回结果上相当，就需要缩小产品投入，或明确专用流程究竟为哪类困难提供额外价值。

## 6 对当前设计的建议

以下建议不改变已经确定的功能范围，优先通过现有 Demo 验证。

| 优先级 | 建议 | 依据与验收方向 |
| --- | --- | --- |
| P0 | 找药仍作为首要入口 | 用已知药名完成查找；无需先建立服药计划、有效期或数量 |
| P0 | 保持位置、时间、来源和状态的层级 | 用户能解释这只是历史观察；无记录不应被理解为没有药 |
| P0 | 保留可结束的未找到流程 | 未找到不强制填写新位置；不自动归零，也不让旧位置重新成为可靠推荐 |
| P0 | 维持同名包装区分 | 使用“家用盒”“随身盒”等明确标签，测试误选和覆盖风险 |
| P1 | 验证现场照片的净收益 | 比较文字与文字加照片的地点辨认结果，同时计入拍照成本 |
| P1 | 测量手工与真实 AI 的总成本 | 等待、核对及改错都计时；模型失败时能继续手工完成 |
| 后续条件触发 | 再考虑扫码、共享、到期与库存 | 扫码取决于建档负担；共享取决于多人实际移动物品；提醒和库存需独立需求证据 |
| 后续条件触发 | 再评估药箱硬件 | 需要观察硬件能记录哪些自然动作及柜外盲区，不以产品名称论证必要性 |

当前可采用的定位表述：

> 为分散存放的常备药留下可追溯的位置线索，帮助你决定先去哪里找；线索失效后可以补充查找结果和新位置。

不建议宣称“首创 AI 药箱”“自动掌握全屋药品位置”“准确库存”或“已减少重复购买”。现有证据也不足以宣称本项目比竞品更省时。

## 7 后续实测方案

优先实测顺序：**收起来 → 收纳先生 → 用户自己的备忘录与固定收纳 → i药管家**。HomeBox、Grocy 用于机制核对；Medisafe、Hero 暂不作为核心找药效率基准。

先进行研究者功能核对，再邀请 3–5 名符合目标条件的人做探索性试用。使用空药盒或模拟包装，设置药箱、抽屉、背包等位置；不涉及真实服药决定。小样本用来发现问题与反例，不计算市场比例或宣称统计显著效果。

| 任务 | 要核对的事实与记录指标 |
| --- | --- |
| 首次建立两盒同名药的记录 | 必填字段、是否需建位置层级、完成时间、修改次数、包装能否区分 |
| 一段时间后查找指定包装 | 是否选对包装与地点、开始寻找前的用时、实际找回结果、翻找位置数 |
| 包装已经移动但未更新 | 页面是否被误读为当前保证；实际找不到时有哪些操作 |
| 反馈未找到并结束 | 是否必须改数量、归档或删除；原记录是否保留；完成时间 |
| 在别处找到并补充新位置 | 能否保留历史、是否误用旧照片、同名包装是否互相影响 |
| 连续 2–4 周自然使用 | 实际发生的找药次数、主动记录时机、漏记与纠错、总维护时间及放弃原因 |

跨方案采用不同但难度相近的包装任务，并交叉安排使用顺序，避免同一药盒重复查找的记忆效应。每个方案应使用其合理的最简配置；不能故意让竞品完成不必要的库存流程。

总体比较采用“录入与维护总时间＋查找与纠错总时间”，同时看找回结果和错误理解，避免只优化某一步。若自然查找发生太少，应延长观察或承认价值证据不足；若备忘录已同样有效，应缩小专用产品范围；若旧线索经常误导，应重新评估核心机制。
