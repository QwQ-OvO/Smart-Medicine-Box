# 家庭药箱位置线索｜产品实践复盘

> 对照「AI 产品研究与策划实习生」实践题中场景 C、需求探索与产品设计、AI Coding 快速原型、验证与复盘的提问逐项回答。

**复盘结论：** 本轮完成了一个可运行、可检查异常的最小产品原型；值得继续投入的前提，是用户试用能显示历史位置线索确实帮助找药，且记录与纠错成本可接受。

## 1. 为什么选场景 C，第一版解决什么

**选择：年轻人 × 家庭常备药。** 选题依据包括探索性访谈、公开资料研究、竞品与替代方案分析：

| 依据 | 对选题和取舍的作用 | 证据边界 |
| --- | --- | --- |
| [探索性访谈](research/P01_家庭备用药收纳与找药_探索性访谈.md) | 参与者描述了跨位置翻找、药品去向不明和不愿逐次登记，让「已知药名但不知道先去哪找」成为首版候选问题。 | 只有一人自述，没有现场找药观察。 |
| [公开研究与方案证据综述](research/家庭药品管理_公开研究与方案证据综述.md) | 家庭药品认知与实际情况可能有差异；录入和融入日常习惯有成本；扫码、RFID、视觉识别只能覆盖特定动作或范围。因此保留未知状态与时间来源，优先低频记录，不预设实时库存或药箱外自动定位。 | 文献涉及其他年龄、疾病和使用环境，不能直接证明本目标用户的需求或本方案效果。 |
| [竞品与替代方案分析](research/家庭药品位置线索_竞品与替代方案分析.md) | 比较 7 个产品和固定收纳、备忘录两类替代方式。位置、照片、AI 录入并非独有能力；将历史线索与「未找到」后的纠正作为待验证侧重点，并把现有工具列为比较基准。 | 主要核对公开功能说明，未实操竞品；「未确认」不等于对方没有该能力。 |

以上材料支持收窄问题，尚未证明普遍需求或本产品优于替代方式。

**第一版的核心问题：** 用户已经知道要找哪盒药，却想不起放在哪里，需要一条有时间、来源且可以纠正的历史位置线索，帮助决定先去哪里找。产品提供查找起点，不承诺实时定位、准确库存或找药效率已提升。药箱暂作主要收纳点与记录入口；药箱外的位置依靠用户输入，当前没有真实硬件。药箱是否有独立价值，仍须与普通备忘录及固定收纳比较。

## 2. 需求探索与产品设计：逐项回答

### 核心用户：第一版先服务谁？

25–35 岁、没有长期固定用药管理需求、家中有分散存放的常备药、需要时才想起寻找的年轻人。这里的年龄和场景是本轮设计筛选条件，不是已经量化验证的人群画像。

### 核心问题：只解决什么，为什么优先？

只解决「已知药品的查找起点与线索纠错」。它回应访谈中的翻找问题；公开研究提示持续录入成本和硬件感知范围有限，竞品比较也显示「AI 录入」本身不足以构成差异。这个问题能在无需自动感知硬件和长期库存维护的条件下形成可运行闭环。没有加入诊断、推荐药品、剂量、服药提醒、有效期、补货或多人同步，因为这些需要不同的用户证据、数据准确性与风险控制；本轮不能从一次找药推导其必要性。

### 核心流程：用户如何完成一次完整任务？

1. 整理药箱或放置药品时，手工填写或用一句话描述「哪盒药在哪里」，可选一张收纳现场照片。
2. 用户核对药名、包装标签、位置和照片后保存；未经确认的解析结果不进入正式记录。
3. 下次需要找药时输入已知药名；同名多盒先选择「家用盒」「随身盒」等具体包装。
4. 查看最近一次位置观察的地点、时间和来源，再去实际寻找。
5. 找到则留下本次找到的反馈；没找到则记录「这里没找到」，可以结束任务，或在别处找到后补充新位置。
6. 新位置成为最新线索，旧位置、照片和查找反馈保留在历史中；刷新后已保存的记录仍可查询。

### 智能能力：AI 在哪一步参与，为什么这样设计？

AI 只参与第 1 步的**文字整理**：尝试从用户原话提取药名和位置，输出待核对字段。它不认定药当前仍在该位置，不推测药是否用完，不决定应该吃什么药。之所以选这一步，是希望减少输入负担；但「输入、等待、核对、纠错」的总成本是否比手工表单低，尚未验证。

默认 Demo 是界面标明的**确定性 Mock 解析**，只覆盖有限句式，不能拿来证明真实模型准确率。真实模型的服务端适配、响应结构校验和超时处理已实现，但尚无真实凭据和模型实测。解析失败、歧义或缺字段时，用户可以补填或转手工流程。共享契约见[packages/contracts/src/index.ts](../packages/contracts/src/index.ts)，解析服务见[apps/api/src/services/parse-service.ts](../apps/api/src/services/parse-service.ts)。

### 关键假设：当前最重要、但尚未验证的判断是什么？

**低频记录在后续查找中带来的收益，能否超过记录与纠错的成本。** 这包含三个待验证环节：用户是否会在自然整理时留下记录；过一段时间后历史线索是否仍有帮助；失效反馈是否让用户少被旧线索误导，而不会造成新的维护负担。单人访谈只能帮助形成假设，自动化测试也不能回答这个产品价值问题。

## 3. AI Coding 快速原型：真实交付与重要异常

### 最小 Demo 是否能完成完整任务？

已实现「输入/操作 → 应用处理 → 解析能力可选参与 → 位置记录和状态变化 → 查找与纠正」的闭环。前端采用 React、TypeScript、Vite；药品、位置观察、反馈和照片保存在本机 IndexedDB；Fastify 后端只处理文字解析，不保存药品记录。运行方式和两分钟演示路径见[README](../README.md)。构建后可在 `http://127.0.0.1:3001` 本机体验；该地址不是公开部署地址。

数据结构刻意区分**具体包装、一次位置观察、一次查找反馈**。新位置不覆盖旧观察，当前线索由最新观察及其反馈推导。照片与某一次观察绑定，不因位置更新而沿用。保存使用事务；命令 ID 避免失败重试产生重复记录；修订号阻止旧页面静默覆盖较新的修改。相关实现见[领域规则](../apps/web/src/domain/medicine.ts)和[本地存储](../apps/web/src/infrastructure/medicine-store.ts)。

### 自行选择的重要异常：按线索没找到

用户到记录地点却没有找到药，是本方案最关键的边界。产品把这次结果记为「在这个位置未找到」，**不**推断药已用完、家中没有库存，也不把更早的位置自动升级为可靠推荐。用户可结束本次查找；若后来在别处找到，则新增位置观察，旧线索和失败反馈继续可追溯。这样用户可以看出依据何时产生、何时失效，而不会被一个被覆盖的“当前位置”误导。

其他已处理的边界包括：无记录时不编造位置；同名多盒先区分包装；解析失败可手工填写；照片处理或保存失败不显示成功；迟到解析响应不覆盖用户已改的草稿。当前本机存储没有账户、同步或云备份，清除浏览器站点数据会删除记录。

## 4. 验证与复盘：已经知道什么，还不知道什么

### 当前最关键、但尚未验证的假设

工程上，闭环和若干异常可执行；产品上，**尚未证明目标用户愿意持续留下足够有用的位置线索，也未证明查找收益高于维护成本**。此外，尚未证明药箱硬件比纯软件入口更必要，或一句话输入比手工表单更省事。

### 如何验证产品或智能能力是否有效？

先用 3–5 位符合场景的用户做探索性试用，让他们独立记录两盒可区分包装、隔天凭线索查找、模拟原位置未找到、再补充新位置。观察独立完成情况、误选包装和误读「历史位置」的次数、记录与查找耗时、纠错动作和求助点。再与用户已有的固定收纳或备忘录比较完整任务的总成本；短时情境试走只能发现交互问题，不能证明长期使用价值。若自然找药很少或备忘录已足够，应缩小甚至停止此方向。

真实模型接入后，应使用明确位置、缺字段、指代、歧义、冲突、医学请求、提示注入和服务失败等样例，检查是否臆造字段、能否要求核对、失败后能否继续手工任务。Mock 的表现不计入真实模型准确率。具体计划见[开发与验证记录](开发/开发与验证记录.md)。

### 已完成的工程验证与限制

[开发记录](开发/开发与验证记录.md)记载：29 条单元/接口测试、9 条 Chromium 浏览器测试、类型检查、构建和构建版冒烟检查通过。覆盖持久化、同名包装、照片历史、解析回退、保存失败重试和并发冲突等行为。这些结果支持「Demo 能运行并按设计处理这些情况」，**不**支持「真人已觉得有用」「真实模型有效」「手机相机已兼容」等结论。真人可用性、真实模型、真机相机、Safari/Firefox、低存储环境仍未实测。

### 如果再给 2 小时，第一件做什么，为什么？

优先邀请一名目标用户在不接受操作提示的情况下完成一次「自然记录 → 查找 → 原位置未找到 → 纠正」试走，并记录误解与操作时间。这个动作直接检验最薄弱的产品假设，特别是用户是否愿意记录、是否把历史位置误认为实时保证。若用户根本找不到自然记录时机，继续增加 AI、OCR 或硬件都不能解决核心问题。之后再决定是减步骤、改文案、转向已有工具，还是继续开发。

## 5. AI 协作说明

**实际投入约 3 小时：本人监督、核对与判断约 1.5 小时，AI 自动化执行约 1.5 小时。**

本人与 AI 的具体分工如下：

1. **选题与 MVP：** 本人先与 AI 讨论五个候选场景，最后收窄并确定场景 C；MVP 的核心问题和范围也是讨论后共同收敛的。
2. **产品设计与原型：** AI 提出产品设计构思，本人再修改、缩小范围，并增加位置拍照这一选择。先在 Figma 画原型是本人提出的工作安排。
3. **技术方案：** 技术选型与数据库表设计由 AI 提出，本人核对其逻辑后决定采用。前后端设计与开发方案由 AI 撰写，本人审阅后认为适合该 Demo，再据此推进。
4. **开发协作：** 本人提供要使用的 **backend-patterns、api-design、test-driven-development** Skills，由 Codex 按讨论后的范围协助实现和验证。Figma MCP 用于读取设计上下文，Vitest 与 Playwright 用于工程验收；这些工具均见[开发记录](开发/开发与验证记录.md)。本人通过审阅方案、检查实现逻辑与运行结果来决定是否接受 AI 产出。
